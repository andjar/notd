`POST /api/v1/ops.php` is the only way to create, change, move or delete notes. The notd frontend uses exactly this endpoint, so anything the UI can do to the outline, a script can do too.

A request carries a list of **operations**. They are applied in order inside one transaction: either the whole batch is applied or none of it.

```bash
curl -X POST http://localhost:8000/api/v1/ops.php \
  -H 'Content-Type: application/json' \
  -d '{"ops": [
        {"op_id": "demo-1", "type": "create", "id": "0192f6a0-7c3e-7b1a-9f3e-2b1c4d5e6f70",
         "page_id": 87, "parent_id": null, "after": null, "content": "Hello"},
        {"op_id": "demo-2", "type": "edit", "id": "0192f6a0-7c3e-7b1a-9f3e-2b1c4d5e6f70",
         "content": "Hello {status::draft}"}
      ]}'
```

## Operations

Every operation has an `op_id` (unique string, at most 64 characters), a `type` and the `id` of the note it acts on.

| `type` | Other fields | Effect |
|---|---|---|
| `create` | `page_id`, `parent_id`, `after`, `content`?, `collapsed`?, `sort_key`? | Creates the note. **The caller chooses the id.** |
| `edit` | `content` | Replaces the content and re-indexes its properties. |
| `move` | `parent_id`, `after`, `sort_key`? | Moves the note (with its subtree) under `parent_id`, right after sibling `after`. |
| `collapse` | `collapsed` | Sets the collapsed flag. |
| `delete` | | Deletes the note and its whole subtree. |

- `parent_id` is the id of the new parent, or `null` for the top level.
- `after` is the id of the sibling the note should follow, or `null` to become the first child.
- A note can only be moved within its own page, and never under itself or one of its descendants.

### Choosing ids

Ids are generated by the caller so that a note can be referred to (as a parent, in a later edit, for an attachment) before the server has answered. Use a UUIDv7 or any other unique string that matches `[A-Za-z0-9_-]{1,64}`.

### Ordering {#ordering}

Siblings are ordered by a fractional `sort_key`, so a move rewrites only the moved note. You do not need to compute keys: say where the note goes with `after` and the server picks the key.

A client that wants to show the result before the server answers can compute the key itself and send it as `sort_key`. The server keeps it if it still lies strictly between the two neighbours and replaces it otherwise. The algorithm is in `assets/js/app/fractional-index.js` (JavaScript) and `api/Ordering.php` (PHP); both produce the same keys.

## Response

```json
{
    "status": "success",
    "data": {
        "results": [
            { "op_id": "demo-1", "status": "applied" },
            { "op_id": "demo-2", "status": "skipped" }
        ],
        "notes": [ { "id": "0192f6a0-7c3e-7b1a-9f3e-2b1c4d5e6f70", "sort_key": "Zz", "content": "Hello", "...": "..." } ],
        "deleted": [],
        "warnings": [
            { "index": 1, "op_id": "demo-2", "id": "nope", "code": "missing",
              "message": "Note no longer exists; edit skipped." }
        ]
    }
}
```

| Field | Meaning |
|---|---|
| `results` | One entry per operation: `applied`, `skipped` (see `warnings`) or `duplicate`. |
| `notes` | The current state of every note the batch touched. Treat it as authoritative. |
| `deleted` | Ids removed by the batch, including descendants. |
| `warnings` | Operations that could not be applied as sent, with a `code`. |

### Retries are safe

The server remembers applied `op_id`s for 90 days. Sending an operation again (for example after a timeout, when you do not know whether it arrived) returns `duplicate` and changes nothing.

### Skipped operations

An operation whose target has disappeared, for example because the note was deleted in another tab, is **skipped with a warning** instead of failing the batch, so unrelated edits in the same request are never lost.

| `code` | Situation | What the server does |
|---|---|---|
| `missing` | The note of an `edit`, `move` or `collapse` does not exist. | Skips the operation. |
| `exists` | `create` with an id that already exists. | Skips the operation. |
| `page_missing` | `create` on a page that does not exist. | Skips the operation. |
| `parent_missing` | The parent does not exist on this page. | `create`: places the note at the top level. `move`: skips. |
| `after_missing` | The `after` sibling is not a child of the parent. | Places the note last. |
| `cycle` | `move` under the note itself or a descendant. | Skips the operation. |

## Errors

| Status | When |
|---|---|
| `400` | The body is not `{"ops": [...]}`, or an operation is malformed (missing `op_id`, unknown `type`, invalid id, `edit` without string `content`, ...). Nothing is applied. |
| `405` | Not a POST request. |
| `413` | More than 500 operations in one request. |
| `503` | The database stayed locked after several attempts. Retry with the same `op_id`s. |
